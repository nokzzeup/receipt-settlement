# 설계 결정 기록

"왜 이렇게 했지?"가 궁금할 때 보는 문서. 결정을 바꾸면 여기에 날짜와 이유를 추가한다.

## 0단계 (2026-10-02 ~ 10-04)

### DB: PostgreSQL + Docker → SQLite
- 처음엔 Docker로 PostgreSQL을 띄웠지만, Windows에서 Docker Desktop 첫 세팅(WSL·가상화·엔진 시작)이 팀원마다 막힐 위험이 커서 뺐다
- 동아리 하나 규모에서는 PostgreSQL이어야만 하는 기능이 없고, "무비용 로컬 실행"이라는 차별점에도 파일 하나짜리 DB가 더 맞는다
- 특정 DB 전용 기능(JSONB 등)은 쓰지 않는다 → `DATABASE_URL`만 바꾸면 PostgreSQL로 돌아간다 (같은 마이그레이션·테스트가 PostgreSQL 16에서 통과하는 것 확인)

### SQLite의 약점은 공통 코드에서 막음 (`backend/app/db/`)
| 약점 | 대응 |
|---|---|
| 시간대 정보를 조용히 버림 (14:32 KST가 그냥 14:32로 저장) | `UTCDateTime` 타입: 시간대 없는 값은 저장 시 에러, UTC로 저장하고 읽을 때 UTC를 붙여서 반환 |
| INTEGER 컬럼에 소수도 그냥 저장됨 | `StrictInteger` 타입: 금액·수량에 int가 아니면 저장 시 에러 |
| 외래키 검사가 기본으로 꺼져 있음 | 연결할 때마다 `PRAGMA foreign_keys=ON` |
| 파이썬 드라이버의 옛날 트랜잭션 방식 (SAVEPOINT 오동작) | SQLAlchemy 공식 권장 방식으로 BEGIN을 직접 관리 |
| 읽기·쓰기가 서로 막음 | WAL 모드 |

- 마이그레이션은 batch 모드(테이블을 새로 만들어 데이터를 옮김). 이때는 일부러 외래키 검사를 끈다 — 켜두면 테이블을 지우는 순간 CASCADE로 자식 데이터(지출 품목 등)가 같이 지워진다
- 위 동작은 `backend/tests/test_db_rules.py`가 검사한다

### Python 3.12/3.13 고정 (3.14 이상 불가)
- 3단계에 쓸 PaddlePaddle(3.3.1)·PaddleOCR(3.7.0)가 Windows·Mac용 Python 3.14 설치 파일을 아직 내놓지 않음 (2026-10-04 확인)
- `npm run setup`이 3.12/3.13이 아니면 이유를 말하고 멈춘다

### 한국어 Windows 인코딩 주의
- Alembic은 `alembic.ini`를 UTF-8이 아니라 OS 인코딩(한국어 Windows는 cp949)으로 읽는다. 한글 주석 하나로 `npm run setup`이 실패했었다
- `alembic.ini`, `requirements*.txt`, `script.py.mako`는 영어로만 쓴다 (`backend/tests/test_repo_files.py`가 검사)

### 도메인 모델 세부 결정
- **행위자는 전부 Membership을 가리킴**: 결제자·업로더·승인 처리자·환급 처리자 컬럼은 `*_membership_id`. 같은 사람도 조직마다 역할이 다르고, `user.id`를 잘못 넣는 실수를 막기 위해서. 조직 생성자만 `created_by_user_id`
- **지출 금액 컬럼 없음**: 품목 금액 합계로 계산 (값이 두 군데 있으면 어긋남). 개인 지출 품목을 빼면 환급액이 자동으로 줄어든다
- **영수증 : 지출 = 1 : 1**: `Expense.receipt_id`는 필수 + 유일
- **DB 제약으로 막는 것**: 환급 정보(일시·처리자)는 함께 있어야 하고 승인(APPROVED) 상태에서만 가능, 수량 > 0, 예산 ≥ 0
- **Enum은 문자열 + CHECK 제약**: DB 고유 ENUM은 값 변경 시 마이그레이션이 번거로움
- **MappingRule 전역 규칙**: 계정과목이 조직마다 따로 있어서 전역 규칙은 특정 계정과목 ID를 가리킬 수 없다 → 이름(`category_name`, 예: "식비")으로 저장하고, 분류할 때 그 조직의 같은 이름 계정과목에 매칭. 조직 규칙은 `category_id`. CHECK 제약으로 둘 중 하나만 허용
- **삭제 정책**: 자동 삭제(CASCADE)는 지출 → 품목·결재 이력, 계정과목 → 매핑 규칙만. 조직·멤버십·영수증·사용 중인 계정과목은 참조하는 데이터가 있으면 삭제가 막힌다 (재무 기록 보존). 조직 삭제·탈퇴가 필요해지면 soft delete로
- **같은 조직 데이터끼리만 연결되는지**(영수증·결제자·계정과목)는 DB가 보장하지 않으므로 API/서비스 계층에서 검증한다

### 인증·조직 (1단계, 2026-10-05)
- **비밀번호**: argon2 해시(`pwdlib`). 8~128자. 이메일은 소문자로 저장해 대소문자 다른 중복 가입을 막음
- **로그인 실패 메시지는 하나로**: "이메일 또는 비밀번호가 올바르지 않습니다." (가입 여부 노출 방지). 없는 이메일도 더미 해시 검증을 돌려 응답 시간 차이를 줄임
- **JWT**: HS256, 유효기간 7일(`JWT_EXPIRE_MINUTES`), 리프레시 토큰 없음 → 만료되면 다시 로그인. 학교 과제 범위에서 충분
- **JWT 비밀키**: `.env`의 `JWT_SECRET`이 비어 있으면 `DATA_DIR/.jwt-secret`에 자동 생성(커밋 안 됨) — 개발용은 `backend/data`, 팀 공용 서버는 `server-data`. 팀원마다 키가 달라도 각자 로컬 DB라 문제없음
- **토큰 저장 위치**: 브라우저 localStorage. httpOnly 쿠키보다 XSS에 약하지만, 같은 출처 프록시 구조·외부 스크립트 없음·과제 범위라 단순함을 택함. 401 받으면 토큰 지우고 로그인 화면으로
- **다른 조직 접근은 404**(403 아님): 조직이 존재하는지조차 알려주지 않음. 멤버지만 역할이 부족하면 403
- **초대 코드**: 8자, 헷갈리는 글자(0/O, 1/I/L) 뺀 31자 알파벳. 입력할 때 대소문자·하이픈·공백 무시. 총무만 조회·재발급 가능, 재발급하면 이전 코드는 즉시 무효. 참여하면 MEMBER
- **조직 생성자는 TREASURER**. 총무는 여러 명 가능하지만 **마지막 총무는 강등 불가**(409) → 조직이 관리자 없이 남는 것 방지
- **역할 변경은 총무만**. 탈퇴·추방은 아직 없음(재무 기록 보존 정책과 함께 나중에 soft delete로)
- **회원가입 직후엔 항상 조직 선택 화면으로**: 로그인은 원래 가려던 주소로 돌아가지만, 새 계정은 소속 조직이 없어서
- **계정과목 등록은 2단계로 이월**: 지출 등록 화면과 같이 만드는 게 흐름상 자연스러움

### 영수증 등록·지출 (2단계, 2026-10-05)
- **업로드하면 바로 '작성 중(DRAFT)' 지출이 생긴다** (영수증 : 지출 = 1 : 1). 확인·수정 화면은 그 지출을 고치는 화면. 중간에 나가도 지출 목록에서 이어서 하거나 삭제할 수 있다
- **OCR·파싱이 실패해도 업로드는 성공**: 빈 값으로 만들고 "직접 입력" 안내. 단, 카드번호 마스킹을 못 거친 OCR 결과는 저장하지 않는다
- **카드번호 마스킹**: 4-4-4-4 / 4-6-5 / 13~19자리 연속 숫자(이미 `*`가 섞인 것 포함) → 마지막 4자리만 남김. 바코드 같은 긴 숫자도 가려질 수 있지만 개인정보 쪽으로 틀리는 게 낫다고 판단. 승인번호(8자리)·전화·사업자번호·금액은 그대로 (`app/receipts/masking.py`)
- **이미지**: 파일 앞부분(매직 바이트)으로 JPG·PNG·WEBP만 받음, 15MB 이하. HEIC(아이폰 기본 형식)는 OpenCV가 못 읽어서 거절 — 브라우저 촬영·앨범 선택은 대부분 JPG로 바꿔서 보내줌
- **원본 이미지는 공개 폴더가 아니라 권한 확인 API로만** 내려준다 (`GET .../expenses/{id}/image`). `<img src>`로는 토큰을 못 보내서 프론트는 토큰을 붙여 받은 뒤 임시 주소(blob:)로 표시
- **image_hash = sha256**(완전히 같은 파일만 같음). 비슷한 사진까지 잡는 유사도 해시(pHash)는 6단계 중복 감지 때 방식·컬럼 결정
- **지출 보기 권한**: 총무·승인자는 조직 전체, 구성원은 내가 올렸거나 내가 결제자인 지출만 (영수증에 개인 구매 내역이 있어서 최소 공개). 다른 사람 지출은 404. 투명성을 위해 전체 공개가 필요하면 바꾸기 쉬움
- **수정·삭제·제출**: 작성 중일 때만, 영수증을 올린 사람 또는 총무
- **결제자**는 같은 조직 구성원 누구로든 지정 가능 (대신 올려주는 경우). 기본값은 올린 사람
- **저장(PUT)은 전체 교체**: 품목도 보낸 목록으로 통째로 바꾼다. 4단계 대비: 자동 분류(AUTO) 결과를 그대로 둔 품목(이름·계정과목 같음)은 AUTO 유지, 사용자가 고른 건 MANUAL
- **할인은 음수 금액 품목**으로 둔다 → 품목 합계가 영수증 합계와 맞음. 화면에 ± 버튼 (폰 숫자 키패드에 '-'가 없는 경우)
- **개인 지출 분리** = 해당 품목 삭제. 영수증 합계는 그대로, 청구 금액(품목 합계)만 줄어든다. 화면에 "○원은 청구에서 빠져요" 표시
- **제출 조건**: 가게명·결제일시·영수증 합계, 품목 1개 이상, 모든 품목 계정과목 지정, 청구 금액 > 0, 청구 금액 ≤ 영수증 합계. 빠진 걸 한 번에 메시지로 알려줌
- **제출(DRAFT → SUBMITTED)은 2단계로 당김**: "지출 등록"의 끝이 제출이라서. 승인·반려·환급과 제출 회수는 5단계
- **결제일시 입력은 분 단위** (화면 datetime-local). 저장하면 초는 00이 됨 → 중복 감지(6단계)도 분 단위로 비교할 것
- **금액 상한 10억 원** (PostgreSQL INTEGER 범위 안에서 합계를 내도 안전하게). 수량 1~10,000, 지출 1건 품목 100개까지
- **기본 계정과목**: 조직을 만들면 식비, 간식·음료, 비품·소모품, 인쇄·홍보, 교통비, 기타가 같이 생김 (`app/classify/defaults.py`). 4단계 전역 매핑 규칙이 이 이름을 기준으로 동작할 예정. 1단계 때 만든 조직엔 없으니 설정에서 추가
- **품목에서 쓰는 계정과목은 삭제 불가**(409) → 이름 변경으로 대응
- **파싱 1차(규칙 기반)를 2단계로 당김**: Mock OCR로도 확인 화면이 채워져야 흐름을 검증할 수 있어서. 행 묶기(y 좌표) → 가게명·날짜·합계 키워드 → 품목은 머리글(상품명·수량·단가·금액) 열 위치로 배정. 3단계에서 실제 PaddleOCR 출력으로 보강
- 라이브러리 추가: `python-multipart` (FastAPI가 파일 업로드를 받으려면 필요)

### 팀 공용 서버 모드 (2026-10-06)
- **여러 명이 같은 데이터를 쓰는 방법 = PC 한 대(팀장 노트북)를 서버로.** 다른 PC·폰은 브라우저로 접속만 (APK·앱 설치 없음). OCR도 서버에서만 돈다
- 실행: `server-windows.bat` / `server-mac.command` / `npm run serve` → setup 확인 → 화면 빌드 → DB 백업 → DB 구조 업데이트 → uvicorn `0.0.0.0:8080` (워커 1개, 자동 재시작 없음)
- **화면 + API를 포트 하나로**: 백엔드가 `frontend/dist`를 같이 내보낸다(`SERVE_FRONTEND`, `app/web.py`). `/api` 밖의 주소는 index.html(SPA), 없는 `/api` 주소는 404
- **운영 데이터 분리**: 실행 스크립트가 `DATA_DIR`·`STORAGE_DIR`을 `server-data/`로 지정 → 개발 DB·로그인 키와 안 섞임. 개발 중 마이그레이션 실험이 운영 데이터를 건드리지 않고, 개발 서버에서 받은 토큰이 공용 서버에서 통하지 않음. 개발 서버와 동시에 켤 수 있음
  - `.env`에 `DATABASE_URL`·`JWT_SECRET`을 직접 넣으면 개발·서버가 같은 값을 쓰게 되므로 비워두는 게 원칙
- **DB 자동 백업**: 서버를 켤 때 DB 구조 업데이트 전에 SQLite 백업 기능으로 (WAL에 남은 최근 저장분 포함) `server-data/backups/`, 최근 10개. 사진은 제외
- **OCR은 한 번에 한 장** (`app/receipts/intake.py`의 잠금). 동시에 올리면 줄 서서 처리
- 포트 8080 (개발용 5173·8000과 안 겹침). `.env`의 `SERVER_PORT`로 변경
- setup은 개발·서버 포트가 모두 비어 있을 때만 진행 (같은 파이썬 환경을 써서, 서버가 켜진 채로 설치하면 Windows에서 실패)
- **지금은 http + 같은 와이파이 전용**. 밖에서 접속·HTTPS·폰 홈 화면 설치는 터널(Tailscale Funnel 등)을 붙일 때 (중간 발표·실사용 테스트 전)
- 모바일을 빼고 PC만 쓰는 안은 채택하지 않음: 폰도 PC와 똑같이 주소로 접속하면 되고, 결제 직후 바로 찍는 게 핵심 흐름이라서. PC 업로드(앨범에서 고르기)는 같이 지원

### 실행 구조
- 루트 `package.json`의 npm 명령 하나로 백엔드와 프론트를 같이 실행 (`concurrently`, Ctrl+C 한 번에 둘 다 종료)
- 더블클릭 실행 파일(`start-windows.bat`, `start-mac.command`): 패키지 목록(requirements·package-lock)의 지문을 `backend/.venv/setup-stamp.txt`에 남겨두고, 바뀌었으면 실행 전에 setup을 자동으로 다시 한다 → `git pull` 후에도 더블클릭만 하면 됨
- `start-windows.bat`은 영어로만 쓴다 (cmd.exe가 OS 인코딩으로 읽음). 한글 안내는 Node 스크립트(`scripts/launch.mjs`)가 출력
- Vite는 `strictPort`: 5173이 이미 쓰이면 다른 포트로 바꾸지 않고 에러 → 주소가 항상 같음
- Vite는 `127.0.0.1`에 고정: 기본값 `localhost`는 Windows에서 IPv6(`::1`)로만 열려서, IPv4로 확인하는 실행 스크립트가 서버를 못 알아보는 문제가 있었음 (2026-10-04). 브라우저 주소는 `http://127.0.0.1:5173` (localhost도 접속은 됨)
- 실행·설치 전에 포트 8000/5173을 먼저 점검: 다른 창에 서버가 켜져 있으면(Windows는 실행 중인 파일을 못 지워서 `npm ci`가 중간에 실패) 또는 Windows가 포트를 예약해둔 경우 이유를 한국어로 알려주고 멈춤
- 프론트는 `/api` 요청을 Vite 프록시로 백엔드(127.0.0.1:8000)에 넘긴다 → CORS 불필요, 폰에서 접속해도 그대로 동작
